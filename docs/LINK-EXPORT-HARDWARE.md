# Link Export 실기 기록

2026-10-15. 원본과 동일한 기준선 `03d3371`을 커밋한 뒤 시험용 네트워크에서 확인했다. 이 기준선은 `port/rbxport-one-to-one` 브랜치에 남긴다. 원본은 rbxport 1.8.0 (`90bfb53da59c5b2c3f0b76101601f30a6b74ab2b`)이다.

## 환경과 범위

- 장비: CDJ-2000nexus 2대, DJM-900NXS2, 시험용 스위치, Mac USB LAN.
- 같은 Mac의 rekordbox·rekordboxAgent가 꺼진 것을 확인하고 실행 중에도 검사했다.
- Link Export 가상 번호는 17, 유선 IPv4 링크 로컬 네트워크를 사용했다.
- 저장소 밖의 실행 도구와 합성 음원을 사용했다. 기존 곡·USB 파일을 수정하지 않았다.
- 실제 곡 로드·재생·CUE 조작은 2번 CDJ에서 확인했다. 1번은 발견·마운트까지만 확인했다.
- 합성 신호 음원: 60초, 120 BPM, 44.1kHz 스테레오. WAV는 PCM 16비트, MP3는 320kbps다. ANLZ는 이식한 author API로 생성했다.

## 결과

| 항목 | 결과·근거 |
|---|---|
| 네트워크 참여 | 가상 번호 17로 참여, CDJ 2대와 믹서 발견 |
| NFS 공유 | 두 CDJ가 Mac 공유를 자동 마운트 |
| 브라우징 | 2번 CDJ의 LINK → Mac → PLAYLIST → DJLinkKit Test에서 시험곡 표시를 사용자 확인 |
| Mac → CDJ 로드 명령 | 2번 CDJ에서 합성 track ID 수신·곡 정보·분석·NFS 요청 확인 |
| MP3 | 60초·120 BPM 표시, 신호 MP3의 시작 위치·재생·CUE 복귀를 사용자 확인 |
| WAV 기준선 | 수동 생성 PCM WAV와 FFmpeg 생성 신호 WAV 모두 E-8305 재현 |
| WAV 응답 비교 | 곡 정보 첫 항목의 id만 1→11로 바꾸자 로드·재생·시작 위치 CUE 복귀를 사용자 확인 |
| 실제 수정 서버 | 임시 응답 보정 없이 WAV 정상 PCM 읽기와 지속적인 loaded/CUE 대기 상태를 확인 |
| 종료·포트 반환 | 서버 정상 종료 후 사용한 UDP/TCP 포트와 실행 프로세스가 남지 않은 것을 확인 |

처음의 완전 무음 MP3는 로드됐지만 사용자가 CUE가 끝에 잡힌다고 보고했다. 작은 신호가 들어 있는 새 MP3로 바꾸자 시작 위치·재생·CUE 복귀가 정상이었다. 무음 구간을 찾는 Auto Cue의 영향으로 추정하며, 이 결과를 서버 큐 목록 기능이 검증됐다는 뜻으로 해석하지 않는다.

## WAV E-8305 원인과 수정

고정 원본의 `rbl-dbserver/src/session.rs::track_info_rows`는 첫 항목의 `a`와 `id`를 모두 1로 고정한다. Swift도 기준선에서 이를 그대로 옮겼다.

실제 CDJ 요청은 `0x2102` 후 `0x3000`, 문맥 `0x02080401`이다. 인자 하나짜리 setup을 사용하는 이 장비에는 첫 항목이 legacy item type `0x04`로 전달된다. 이 첫 항목의 `arguments[1]` 값이 디코더를 선택하는 것으로 관측됐다.

| 동일 신호 WAV에서 바꾼 것 | 관측 |
|---|---|
| 기준선, 첫 항목 id=1 | E-8305. NFS 파일 경로 조회 성공, 관측한 READ 응답은 파일 바이트와 일치 |
| 별도 0x2f 항목의 값만 11 또는 3 | 같은 실패. 이 필드를 WAV 수정 근거로 사용하지 않음 |
| 첫 항목 id만 11 | RIFF 헤더 64바이트·PCM 블록 읽기로 전환, 정상 CUE 대기 및 사용자 재생·복귀 확인 |
| 실제 서버가 `TrackDetails.file_type`을 전달 | 응답 보정 없이 같은 정상 읽기·CUE 대기 확인 |

첫 항목의 `a` 값 1과 나머지 항목·바이트는 유지한다. `file_type`이 0인 기존 Source·원본 시험에는 기존 기본값 1을 유지한다. 이식 기준선 후의 수정으로 PLAN §9에 기록했다. 실제 형식 값 1(MP3)·11(WAV)을 이 장비에서 확인했으며 다른 형식·장비의 전체 호환성을 확인한 것은 아니다.

### 회귀 시험

`TrackInfoCompatibilityTests.swift`는 원본에 없는 별도 실기 회귀 2개다. 실제 setup/track-info/render 왕복을 가짜 세션으로 준비하고 인코딩된 첫 응답과 경로·track ID를 검사한다.

- WAV 시험은 수정 전 첫 항목 id=1에서 실패, 수정 후 id=11에서 통과했다.
- MP3와 형식 미지정 입력의 기존 응답이 유지되는 것도 검사한다.
- 원본 대응 시험(당시 469개, 이후 502개)의 이름·순서·입력·기대값은 바꾸지 않았다.
- 수정 직후(2026-10-15)의 전체 로컬 CI: 등록 1,479개, 조건부 건너뜀 15개, 실패 0. 지금 선언된 시험 수와 다른 이 숫자는 그날의 기록이다.

## 송수신 확인 방법

시스템 BPF 캡처는 권한이 없어 실행하지 못했다. 실행 도구에서 주입한 실제 TCP/UDP 소켓의 송수신 경계에 기록을 붙여 요청·응답을 비교했다. 관측한 NFS READ 응답의 데이터는 해당 합성 파일의 같은 offset 바이트와 일치했다. 이것은 애플리케이션 송수신 기록이며, 시스템 pcap 캡처라고 부르지 않는다.

기록용 경계와 응답 필드 실험은 저장소 밖의 임시 도구에만 두었다. 실제 펌웨어·rekordbox 실행 파일을 분석하지 않았다. 개인 곡·경로·IP/MAC·캡처 파일은 공개 저장소에 복사하지 않았다.

## 남은 확인

- 레거시 큐 목록 `0x2104` 읽기는 고정 원본과 Swift 기준선 모두 미지원이었다. 첫 실기에서 실제 요청과 generic unsupported 응답을 확인했고, MP3/WAV 기본 로드·재생은 성공했지만 큐 복원은 되지 않았다. 이후 [#20](https://github.com/ImBada/DJLinkKit/issues/20)에서 구현했고, 같은 날 CDJ-2000nexus에서 메모리 큐·루프·Hot Cue A/B/C 호출을 확인했다(확인함, 2026-10-15). 큐 순서 문제와 아직 재현하지 못한 메모리 큐 소실은 [#20 기록](LINK-EXPORT-LEGACY-CUES.md)에 있다.
- CDJ-3000 계열·다른 음원 형식·핫 큐/메모리 큐 편집·장시간 연속 스트리밍은 이번 실기의 확인 범위에 포함하지 않는다.
- 현재 CLI에는 서버 시작 명령이 없다. 실기는 별도 임시 실행 도구로 했다. 재사용할 실행 도구·앱 연결은 별도 작업이다.
