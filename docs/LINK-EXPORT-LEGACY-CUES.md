# 레거시 큐 목록 읽기 (#20)

2026-10-15. [이슈 #20](https://github.com/ImBada/DJLinkKit/issues/20)의 구현·검증을 기록한다. 사용자의 구현 완료·검증 진행 신호 뒤 **추가 회귀 8개(`LegacyCueReadTests` 6 + `LegacyCueClientTests` 2)와 전체 CI가 통과**했다. 처음 7개였다가 실기에서 찾은 큐 순서 문제를 고치며 1개를 더했다. 실제 CDJ의 요청·응답을 확인했다. 첫 실기에서 핫큐 A 버튼이 꺼지고 CALL ▶가 E-8302를 내는 문제를 찾아, 큐 목록 순서를 고친 뒤 메모리 큐·루프·A/B/C 호출을 모두 확인했다.

## 확인한 계약

- 요청 `0x2104`: 숫자 인자 `[문맥, track ID]`. 이전 CDJ-2000nexus 실기의 문맥은 `0x02080401`이었다.
- 응답 `0x4702`: 요청 종류·상태·레코드 바이트 수·레코드·레코드 길이 `0x24`·hot/memory 개수·sidecar 길이/바이트·빈 후행 데이터.
- 36바이트 레코드에서 cue/loop와 hot 버튼, 150fps 단위 위치를 공개 클라이언트가 읽는다. 기존 서버의 sidecar는 밀리초 위치를 담는다.
- 빈 목록은 정상적인 빈 응답으로 제공한다. 숫자 문맥·track ID가 없는 잘못된 요청에는 기존 사용 불가 응답을 보낸다. 잘못된 요청은 카탈로그를 읽지 않는다.

근거는 이미 이식한 MIT alphatheta-connect의 [`message/types.ts`](https://github.com/chrisle/alphatheta-connect/blob/7496991060a38951c2119db13c26b3da7c075bfa/src/remotedb/message/types.ts), [`queries.ts`](https://github.com/chrisle/alphatheta-connect/blob/7496991060a38951c2119db13c26b3da7c075bfa/src/remotedb/queries.ts)의 `getCueAndLoops`, 기존 Swift 클라이언트의 `RemoteDBResponse.swift`다. 응답 본문은 고정 GPL 원본 rbxport의 기존 `usb_cue_reply`를 재사용한다. 새로운 실행 파일 분석이나 미확인 레코드 형식을 도입하지 않는다.

## 구현 범위

`kind.CUES`와 `CUES_REPLY`를 추가하고 요청을 기존 큐 목록 인코더에 연결했다. 읽기에서 저장·삭제·편집 콜백을 부르지 않는다. 저장 요청·Hot Cue Bank·확장 큐 목록 처리와 응답 생성은 그대로 둔다.

라이브러리 어댑터의 입력은 기존 `Library.cues`다. 메모리 cue/loop와 레거시 A/B/C hot cue/loop를 기존 규칙으로 내보낸다. D 이후 hot slot 제외 등 기존 어댑터의 의미를 변경하지 않는다. 호출자는 읽힐 큐를 스냅샷에 제공해야 한다.

## 추가 회귀 시험

| 파일 | 작성 개수 | 확인하려는 경계 |
|---|---:|---|
| `LegacyCueReadTests.swift` | 6 | 실제 요청 문맥, 응답 개수·레코드·hot/memory 수, 시간순으로 섞은 입력의 메모리 큐 먼저 정렬, 빈/없는 곡, 곡/트랜잭션 구분, 잘못된 인자, 밀리초 sidecar, 편집 미호출 |
| `LegacyCueClientTests.swift` | 2 | 메모리 라이브러리 → 서버 세션 → 기존 Swift 클라이언트의 가짜 TCP 왕복, 메모리·A/B/C·루프와 D 제외, 빈 binary와 없는 곡 |

기존 원본 대응 469개와 그 입력·기대값은 수정하지 않았다. 자체 회귀는 앞선 WAV 회귀 2개에 이번 8개를 더해 10개이며, `export-test-map.json`의 `regressions`에서 별도로 관리한다. 추가 8개는 모두 통과했다. 그날의 전체 로컬 CI는 등록 1,487개(기존 1,008 + 원본 대응 469 + WAV 회귀 2 + 이번 8), 기존 조건부 건너뜀 15개, 실패 0이며 TypeScript 622개·파일 44개와 Rust 469개의 정적 대응도 통과했다. 이 숫자는 그날의 기록이고 현재 선언 수는 [검증 기록](LINK-EXPORT-VALIDATION.md)에 있다. 자동 시험은 가짜 소켓으로 실행했고 실제 LAN을 사용하지 않았다.

## 실기 송수신

시험용 LAN, rekordbox 계열 프로세스 종료, 가상 번호 17에서 2번 CDJ-2000nexus에 새 합성 곡 `Cue Read Test MP3`(track 20001)를 로드했다. 실제 요청 문맥은 `0x02080401`이었다. 읽기 응답은 상태 0, 레코드 216바이트(36 × 6), hot 3·memory 3, sidecar 48바이트(8 × 6), 빈 후행 데이터로 전송됐다. 해당 요청에 unsupported 보고는 없었다. 임시 도구의 응답 보정 기능을 제거하고 제품 코드를 그대로 사용했다. 이는 애플리케이션 소켓 송수신 기록이며 pcap 캡처가 아니다.

입력은 메모리 큐 0초·10초, 메모리 루프 20–24초, Hot Cue A 5초·B 15초·C 루프 30–34초다. 음원은 앞서 재생을 확인한 60초·120 BPM 합성 신호 MP3를 재사용했다. 메모리 큐와 Hot Cue A/B/C가 화면에 모두 표시되는 것을 사용자가 확인했다. 이 첫 실기에서는 위치 이동·루프 끝을 확인하지 못했다. 이 항목은 아래 "순서 문제와 수정"에서 큐 순서를 고친 뒤 확인했다(메모리 큐 ▶로 10초, 루프 20~24초 반복, A=5초·B=15초·C=30초 루프).

### 순서 문제와 수정 (2026-10-15, CDJ-2000nexus 2번 덱)

처음 실기에서 시간순으로 섞어 보낸 큐 목록(메모리 0초, A 5초, 메모리 10초, B 15초, 메모리 루프 20~24초, C 루프 30~34초)은 증상이 있었다. 핫큐 A 버튼만 꺼지고 화면의 A가 깜빡였으며, 메모리 CALL ▶가 10초가 아니라 A(5초)로 가서 재생을 시작했다. 이어 E-8302(C7AC)가 났고 이머전시 루프에 들어간 적도 있었다.

큐 구성만 다른 합성곡으로 가른 결과다. 모두 같은 MP3와 같은 서버를 썼다.

| 시험곡 | 확인 |
|---|---|
| 큐 없음 | CALL ▶는 "포인트 없음", 오류 없음 |
| 메모리 큐만(0·10초·20~24초 루프) | ▶로 10초, 한 번 더 20초 루프, PLAY 시 20~24초 반복, 오류 없음 |
| 핫큐만(A·B·C 루프) | 화면과 물리 A/B/C 불 정상, CALL ▶는 "포인트 없음"(CALL은 메모리 큐만 부른다) |
| 섞음, 시간순(수정 전) | A 불 꺼짐, CALL ▶가 A로 이동·재생, E-8302 |
| 섞음, 메모리 먼저(수정 후) | A/B/C 불 모두 켜짐, ▶로 10초(정지), 한 번 더 20초 루프, A=5초·B=15초·C=30초 루프 모두 정상, 오류 없음 |

해석은 CDJ가 응답의 hot 개수·memory 개수와 상관없이 **앞의 memory 개수만큼의 레코드를 메모리 큐로** 읽는다는 것이다. 시간순 입력에서 메모리 목록이 [0초, A, 10초], 핫큐 목록이 [B, 루프, C]가 되어 위 증상이 모두 맞는다. 레코드 자체의 형식은 그대로고 순서만 바꿨다. 이 해석은 관측과 맞는 가설이며 CDJ 내부를 분석한 것은 아니다.

수정은 읽기 핸들러(`cue_list`)에서만 메모리 큐(버튼 0)를 앞에, 핫큐를 뒤에 보내는 것이다. 각 그룹 안은 시간순이다. 저장 요청(`0x2105`)의 응답은 원본 그대로다. 회귀 시험 `시간순으로 섞인 메모리 큐와 핫큐도 메모리 큐를 앞에, 핫큐를 뒤에 보낸다`는 수정 전 코드에서 실패하고 수정 후 통과한다.

### 메모리 큐 소실 원인 (2026-10-16, #32)

처음 실기(track 20001)에서 메모리 큐가 모두 사라진 구간에 `0x2105`(op 0, 메모리 10초 레코드)가 들어왔었다. 순서를 고친 뒤 버튼을 하나씩 눌러 원인을 확인했다(CDJ-2000nexus 2번 덱, 시험곡 20003, 서버 로그에 시각을 붙여 대조).

| 조작 | CDJ 요청 | 서버 응답 | CDJ 화면 |
|---|---|---|---|
| CUE/LOOP CALL ▶ 2회, ◀ 1회 | 없음 | — | 0초→10초→20초 루프→10초 이동, 큐 유지 |
| 10초 메모리 큐에서 DELETE (Source가 편집 거절) | `0x2105` op 0, 10초 메모리 레코드 | `0x4702` 상태 0x32, 빈 목록 | **메모리 큐 전부 사라짐** |
| 같은 조작 (Source가 편집 수락, 수정 전) | 같음 | 상태 0, 시간순 목록(hot 3·memory 2) | 10초만 지워지지만 **Hot Cue A 불이 꺼짐** |
| 같은 조작 (Source가 편집 수락, 수정 후) | 같음 | 상태 0, 메모리 먼저(hot 3·memory 2) | 10초만 지워지고 A/B/C 유지 |
| 재생 중 12초에서 멈추고 MEMORY (편집 수락, 수정 후) | `0x2105` op 1 | 상태 0, 메모리 먼저(hot 3·memory 3) | 새 메모리 큐 추가, A/B/C 유지 |

- 처음 증상은 CALL이 아니라 **DELETE**에서 나온 것이다. CALL ▶·◀만으로는 `0x2105`가 오지 않았다.
- 편집을 거절하면 원본 rbxport는 상태 0x32와 빈 목록으로 답하고(원본 시험 `cue_writes.rs`가 고정, 원본 주석은 rekordbox의 응답과 같다고 적었다), CDJ는 그 빈 목록대로 메모리 큐 표시를 모두 지운다. Source의 데이터는 바뀌지 않으므로 곡을 다시 올리면 큐가 돌아온다. 원본과 같은 응답이라 바꾸지 않았다. 편집을 거절하는 Source(`StaticSource`, 이번 시험 도구 기본 모드)에서만 생긴다.
- 편집을 받아들인 응답도 읽기 응답처럼 시간순이면 CDJ가 앞의 memory 개수만큼을 메모리 큐로 읽어 핫큐 하나가 메모리 목록에 들어갔다. 편집 응답도 메모리 큐를 먼저 보내도록 고쳤다(PLAN §9). 회귀 시험 `받아들인 큐 편집의 응답도 메모리 큐를 앞에, 핫큐를 뒤에 보낸다`는 수정 전 코드에서 실패하고 수정 후 통과한다.

### 도구 한계

- 실기는 저장소 밖 임시 실행 도구로 했다(합성 신호 MP3와 합성 큐만 사용). 이 도구와 서버가 같은 Mac에서 가상 번호 17로 참여한다. 같은 Mac에서 `djlink status`를 함께 돌리면 CDJ가 가상 CDJ 쪽으로 보내는 유니캐스트 상태 패킷이 한 소켓에만 전달되어, `djlink`에는 CDJ 상태가 보이지 않는다. 장비 문제가 아니다.
- 이머전시 루프·E-8302 뒤에는 서버를 껐다 켜 새로 마운트를 맺게 한 뒤 곡을 다시 올리면 복구됐다.
- pcap 캡처는 sudo가 없어 하지 못했다. 위 판정은 서버가 본 요청 기록과 사용자가 본 화면·버튼에 근거한다.
